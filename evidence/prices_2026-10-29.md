## 2. Limits and behaviors (quoted)

### Kinesis on-demand scaling
Source: https://docs.aws.amazon.com/streams/latest/dev/how-do-i-size-a-stream.html
- "A data stream in the on-demand mode accommodates up to double the peak write throughput observed in the previous 30 days. As your data stream's write throughput reaches a new peak, Kinesis Data Streams scales the data stream's capacity automatically."
- "However, write throttling can occur if your traffic increases to more than double the previous peak within a 15-minute duration. You need to retry these throttled requests."
- "When the incoming traffic exceeds 500 KB/s per shard, it splits the shard within 15 minutes."
- "If your incoming traffic exceeds twice your prior peak, you can experience read or write exceptions for about 15 minutes, even when your data is distributed evenly across the shards."
- "You get at least twice the write throughput compared to read data using the `GetRecords` API."
- Advantage mode: "Enabling On-demand Advantage commits the account to at least 25MiB/s of data ingest and 25MiB/s of data retrieval across all on-demand streams." Minimum 24 hours before disabling.

### Kinesis default and shard limits
Source: https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html
- "By default, new data streams created with the on-demand capacity mode have 4 MB/s of write and 8 MB/s of read throughput. In US East (N. Virginia), US West (Oregon), and Europe (Ireland) AWS Regions, data streams with the on-demand capacity mode scale up to 10 GB/s of write and 20 GB/s read throughput."
- (Record rate for the on-demand default of 4,000 records/s: NOT stated on this page; the docs only give 4 MB/s write. See Could not verify.)
- Provisioned: "Each shard can support up to 1 MB/sec or 1,000 records/sec write throughput or up to 2 MB/sec or 2,000 records/sec read throughput."
- "Each shard can support up to five read transactions per second. Each read transaction can provide up to 10,000 records with an upper quota of 10 MB per transaction."
- "Each shard can support up to a maximum total data read rate of 2 MB per second via GetRecords."
- "By default, you can create up to 50 data streams with the on-demand capacity mode."
- "The default shard quota is 20,000 shards per AWS account" for us-east-1 (provisioned).
- EFO: "up to 20 registered consumers" (Standard, Provisioned); 50 with Advantage.
- Max record 10 MiB; mode switch twice per 24 hours.

### Lambda + Kinesis event source mapping
Sources: https://docs.aws.amazon.com/lambda/latest/dg/with-kinesis.html and https://docs.aws.amazon.com/lambda/latest/dg/services-kinesis-parameters.html
- "Standard iterator: Lambda polls each shard in your Kinesis stream for records at a base rate of once per second."
- "you can tell the event source to buffer records for up to 5 minutes by configuring a batching window" (parameters page lists MaximumBatchingWindowInSeconds default 0; max is stated as 5 minutes = 300 s in the with-kinesis page).
- "You can specify the number of concurrent batches that Lambda polls from a shard by using a parallelization factor from 1 (default) to 10."
- Parameters table: BatchSize default 100, "Maximum: 10,000"; BisectBatchOnFunctionError default false; DestinationConfig: "Amazon SQS queue or Amazon SNS topic destination for discarded records"; TumblingWindowInSeconds "Minimum: 0, Maximum: 900"; MaximumRetryAttempts default -1, max 10,000; MaximumRecordAgeInSeconds default -1, max 604,800.
- "Lambda processes records in each shard in order. It stops processing additional records in a shard if your function returns an error."
- Same page, next sentence after the base rate (fetched 2026-10-30): "When more records are available, Lambda keeps processing batches until the function catches up with the stream."

## 5. Added 2026-10-30 (round-3 review)

### ClickHouse row policies
Source: https://clickhouse.com/docs/sql-reference/statements/create/row-policy (fetched 2026-10-30)
- "A user to whom no condition applies therefore sees every row." This depends on `access_control_improvements.users_without_row_policies_can_read_rows`, which the page describes as "enabled by default".
- "By default, policies are combined using the boolean `OR` operator." "Restrictive policies are combined using the boolean `AND` operator." A row is visible when at least one permissive condition and every restrictive condition is true.
- Consequence used in `schema/access.sql`: a permissive `USING 0 TO ALL` makes every user subject to some policy without widening anyone's rows; a restrictive one would hide every row from every user.
